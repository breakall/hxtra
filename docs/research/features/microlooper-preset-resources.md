# Preset-dependent NAM / Atmosphere resources

2026-11-14 analysis. Scope: the revised requirement that enabling Atmosphere support in firmware must preserve the ordinary NAM capacity in presets without a Atmosphere block: NAM3 without GR, NAM2 with GR. A preset containing Atmosphere may admit fewer NAM blocks, through ordinary browser graying based on its actual blocks. No custom Atmosphere instance cap or warning is requested. This note evaluates allocation and code placement; it does not qualify a replacement firmware.

**2026-11-15 update:** the [implemented external ISA placement](microlooper-code-placement.md)
now fits Atmosphere beside unchanged baseline NAM profiles. The fixed-NAM1 findings
below describe the superseded development layout. No NAM relocation was needed.
Hardware fetch timing and general runtime memory admission remain separate gates.

Evidence uses [the repository conventions](../conventions.md). **[verified offline]** means source inspection, arithmetic from assembled sections, or bounded execution of firmware instructions. **[verified on unit]** below refers to cited historical measurements. **[hypothesis]** marks proposed designs and unproven conclusions. No hardware access, preset write, RAM run, installation or flashing was performed for this note. Only this research note was added.

## Finding

**[verified offline]** The current experimental image does not meet this requirement. [build.py, `kernel`](../../../build.py#L77) selects a compiled one-slot NAM kernel whenever Atmosphere support is enabled; [the linker](../../../tools/patch_microlooper_build.py#L71) requires that exact kernel. The [M4 wrapper](../../../src/m4/nam_capacity.s#L1) is supplied the fixed compiled capacity. Its check cannot create missing NAM storage. Making its limit depend on whether a Atmosphere object exists would admit NAM instances that the installed one-slot kernel cannot hold; that kernel's exhausted-slot behavior is dry passthrough, not another allocated NAM instance. Sources: [slot claims and `m_noslot`](../../../tools/sharc/nam_multi_kernel.asm#L146), [explicit capacity installer](../../../tools/nam_capacity.py#L16).

**[verified offline]** There are three separate constraints: execution storage in SHARC internal RAM, per-instance arenas and DSP time, and bytes in Entry 2's boot stream. Declared DSP costs account for blocks in a preset; they do not move statically linked instructions or NAM slots. The current full Atmosphere code resides permanently in internal Block 3, even when no Atmosphere instance is present. Zero-data LDR compaction changes boot encoding, while leaving initialized memory identical. Sources: [Atmosphere placement](../../../tools/patch_microlooper_build.py#L87), [native cost accounting](../m4/dsp-cost.md), [LDR compactor](../../../tools/sharc/ldr_compact.py#L1).

**[hypothesis / recommendation]** Preserve the normal NAM3/NAM2 kernel as the acceptance baseline. First prove a small memory-placement change that retains those capacities and provides a valid home for all Atmosphere instructions. Reuse native private arenas where they actually fit, but do not treat the allocator as a general unbounded shared heap. A count/admission patch becomes appropriate only after its accepted combinations have real executable storage. No drop-in native-allocation change currently establishes the revised behavior.

## What NAM owns today

**[verified offline]** [nam_multi.Layout](../../../tools/sharc/nam_multi.py#L165) allocates a fixed number of slots in the otherwise free Block 3 tail. A slot contains 74 state/base words, a 1,943-word model/silence stream, head rings, and short convolution rings. A small fixed table maps slot indices to absolute addresses. Each NAM instance stores an index in its native DM and claims a slot by its I0 owner address. These slots are reserved at boot; they are not obtained from the native per-instance allocator when the corresponding block is inserted. Sources: [slot layout](../../../tools/sharc/nam_multi.py#L284), [kernel ownership contract](../../../tools/sharc/nam_multi_kernel.asm#L10), [boot initialization](../../../tools/sharc/nam_multi.py#L343).

**[verified offline]** Existing NAM already uses native private memory for selected rings: DM from the instance's I0 arena, PM from its I8 arena, and long rings/history/sentinels from descriptor words 6/7 in SDRAM. Thus moving an object to private memory is an established seam, but moving all fixed slots there has not been implemented. Sources: [layout selection](../../../tools/sharc/nam_multi.py#L174), [native base binding at `m_init`](../../../tools/sharc/nam_multi_kernel.asm#L1234), [SDRAM lookup](../../../tools/sharc/nam_multi_kernel.asm#L222).

**[verified offline]** Recomputed on 2026-11-14 using `nam_multi.layout(['--mid-sweep', '--slots', str(n)])` and the assembled production Atmosphere sections:

| Compiled NAM slots | Internal words per fixed NAM slot | Private DM words per instance | Private PM words per instance | SDRAM declared per instance | Block 3 gap before other features |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 4,760 | 819 | 0 | 18,432 | 7,290 |
| 2 | 4,760 | 819 | 0 | 18,432 | 2,528 |
| 3 | 3,824 | 771 | 327 | 19,456 | 512 |

The three-slot layout moves additional rings to SDRAM (`FAR_D=17`, versus 41 in the one-/two-slot layouts). It is not three copies of the one-slot layout. All three mid-sweep variants have 1,096 hot and 309 cold instructions. Block 2 ends at `0xc7ffc`, leaving four normal words there. Sources: [thresholds and private budgets](../../../tools/sharc/nam_multi.py#L100), [layout arithmetic](../../../tools/sharc/nam_multi.py#L165), [SDRAM rounding](../../../tools/sharc/nam_multi.py#L340).

**[verified offline]** Using [`microlooper.profile`](../../../tools/sharc/microlooper.py#L111), the actual remaining Block 3 gaps after reserving click and GR where applicable are:

| Baseline profile | Gap in normal 32-bit words | Complete Atmosphere code required | Deficit |
| --- | ---: | ---: | ---: |
| NAM3 + click, no GR | 299 | 1,854 | 1,555 |
| NAM2 + GR + click | 1,077 | 1,854 | 777 |
| NAM1 + GR + click | 5,841 | 1,854 | fits |

Atmosphere comprises 1,099 core, 101 bridge and 33 callback instructions; individually even-padded they occupy 1,236 48-bit instructions, or 1,854 normal words. These gaps use the physical PM/normal-word conversion, not an incorrect one-word-per-instruction count. GR's data and code are placed directly above the fixed NAM slots, and click below NAM's cold code. Sources: [Atmosphere counting and placement](../../../tools/patch_microlooper_build.py#L87), [PM conversion](../../../tools/sharc/microlooper.py#L77), [GR placement](../../../tools/patch_comp.py#L333), [click placement](../../../tools/patch_click.py#L184).

## Native allocation: proven seam and real limits

**[verified offline]** The native composite constructor selects its member array at `0x177f22`. The bounded original-instruction replay at `0x177f8c` copies the parent descriptor and carves child DM, PM and SDRAM ranges from member fields 13/14/15, rejecting requests past each supplied parent end. Native process-record construction (`0x178139`), binding (`0x17827d`) and ISA dispatch (`0x8cb37`) carry the allocated DM base into I0 and the PM base into I8. This proves a useful runtime binding mechanism; it does not prove extra capacity beyond the supplied parent arenas. Sources: [replay](../../../tools/sharc/microlooper_allocation.py#L20), [binding composition](../../../tools/sharc/microlooper_allocation.py#L144), [boundary tests](../../../tests/test_microlooper_allocation.py#L20).

**[verified offline / reproduced here]** Running those spans on Entry 2 extracted from the current experimental HXF produced successful allocation for 199 DM, zero PM and 48,000 SDRAM words, including exact parent boundaries. A 198-word DM parent and a 481-word request from a 480-word PM parent were refused. Guard words survived; process I0 equaled the carved DM base. Entry 2 SHA-256: `a2fdb785570835cf057d36088a63a52a523daf2eb9cfba166d18208627d48f27`. The replay's parents, selected member and audio pointers were synthetic. Complete outer graph traversal, native heap acquisition and physical stereo channel layout were not executed. Source: [replay entry points and explicit limitations](../../../tools/sharc/microlooper_allocation.py#L1).

**[verified offline]** The current host placeholder budgets are:

| Model host | DM words | PM words | SDRAM words |
| --- | ---: | ---: | ---: |
| Mono FX / NAM Distortion | `0x38b` = 907 | `0x14e` = 334 | `0x60400` = 394,240 |
| Stereo FX / Atmosphere | `0x3a2` = 930 | `0x1e0` = 480 | `0x63000` = 405,504 |
| Amp placeholder | `0x596` = 1,430 | `0x1fa` = 506 | initially `0x800`; SDRAM can be raised within the parent slot |

These are the model-tree budgets enforced by existing patch tools, not a claim that arbitrary block-local metadata can enlarge the actual parent. Sources: [`FX_BUDGET` and checked replacement](../../../tools/kit_patch_amp.py#L1178), [amp placeholder and SDRAM propagation](../../../tools/patch_amp.py#L1172).

**[verified offline]** NAM3 already consumes 771 DM + 327 PM words in the mono host, leaving only 143 words under those maxima, versus a 3,824-word fixed slot still to relocate. NAM1/2 leave 422 words, versus a 4,760-word slot. Even the sum of both entire mono budgets is only 1,241 words. A complete slot therefore cannot be moved unchanged into the existing native DM/PM allocations. Enlarging only the member's declared sizes will exhaust a parent and fail construction; it does not borrow other slots' unused memory. Sources: the two preceding measured/source tables and the [constructor's actual exhaustion checks](../../../tools/sharc/microlooper_allocation.py#L28).

**[verified on unit / historical]** Runtime heap pointers are not an available-memory meter. Measurements found whole slot budgets carved even for a one-block preset; Block 1 comprised eight 2,571-word arenas. A crowded stock preset filled some arenas, so their apparent slack could not safely be reassigned globally. Separate NAM instances were allocated in creation order, not screen order. Sources: [heap measurements](../KIT_HEAP_USE.md), [native pointer observations](../KIT_UNIT_MEASUREMENTS.md). **[hypothesis]** Repartitioning parent DM/PM arenas might be possible, but it is a deeper allocator/graph change requiring proof across ordinary stock effects, not a small NAM metadata edit.

## Placement options and their proof gates

**[hypothesis / first bounded investigation]** Try permanent Atmosphere code placement outside the NAM slot region before introducing runtime code overlays. Search for removable fixed state, split private working state, or a native PM allocation that can host a relocated subset with a small resident trampoline. Preserve the existing NAM arithmetic and all baseline slot storage where possible. This is the simplest architectural direction because code residency need not depend on which preset is running. It is not yet a fit result: Atmosphere's full 1,854-word code footprint exceeds its present 480-word stereo PM budget, and NAM's remaining private DM/PM capacity is small. Private PM storage also needs an explicitly proven mapping between the descriptor's data-word address and executable 48-bit PM addresses, code copy/relocation, cache visibility, native construction order and teardown/publication. A native process I8 pointer alone proves none of these loader properties. Sources for the arithmetic: the tables above; for what is actually bound: [process replay](../../../tools/sharc/microlooper_allocation.py#L144).

**[hypothesis / leading data-relocation candidate]** Move the model stream (1,943 words per NAM, including weights and silence state) into each instance's native SDRAM, keeping small frequently accessed metadata private or internal. Removing the whole stream from three fixed slots would release up to 5,829 internal words, comfortably above Atmosphere's 1,854-word code footprint. The existing shared WBUF already stages near-layer weights; extend staged loading to weights still read directly, then separate stream-base addressing from ring/state-base addressing. This avoids swapping an entire mutable slot on each instance switch. The stream is not wholly immutable: load/calibration adjusts its head scale, and head/silence/rechannel accesses need explicit treatment. Saving 1,943 words per slot is therefore an upper-bound layout calculation, not an implemented saving. Prove exact retained metadata, native SDRAM declarations, bounded DMA scheduling, alias-free buffers, bit-exact output and additional worst-case hardware latency before claiming NAM3 capacity is preserved. New copy/DMA instructions must also pass the nearly full Entry 2 guard. Sources: [stream definition and placement](../../../tools/sharc/nam_multi.py#L284), [layer weight offsets](../../../tools/sharc/nam_multi.py#L365), [weight staging and direct stream accesses](../../../tools/sharc/nam_multi_kernel.asm#L433), [load-time scale mutation](../../../tools/sharc/nam_multi_kernel.asm#L1388).

**[hypothesis / fallback feasibility experiment]** One fixed internal NAM working slot could be backed by each NAM instance's own SDRAM. On an owner change, save the outgoing slot and restore the incoming one, leaving the permanent Atmosphere code in a known nonoverlapping region. This reuses NAM's existing owner/base and bounded DMA machinery while allowing several logical NAM instances. It changes state residency, not the number of native Atmosphere instances. However, a full one-slot context is 4,760 words; alternating owners could require roughly 9,520 extra transferred words per NAM call before ring traffic. At 3,000 calls/s per instance, this is substantial and unmeasured. Initialization, dirty state, model changes, DMA failures, repeated owner addresses and bounded return must remain correct. It cannot be described as preserved NAM3 behavior until timing admits the ordinary three-NAM preset and its previously supported neighbors. Sources: [slot contents](../../../tools/sharc/nam_multi.py#L284), [DMA/failure contract](../../../tools/sharc/nam_multi_kernel.asm#L24), [historical real NAM load](../NAM_LITE_DSP_LOAD.md).

**[hypothesis / alternative]** External executable/VISA code could relieve internal pressure, especially for control-rate work. Stock registry callbacks already use VISA in DDR2, but that fact does not establish that the assembled ISA Atmosphere audio core can be copied unchanged to external RAM with acceptable fetch timing. The 33 callback instructions alone save only 51 normal words with padding, far below either baseline deficit. An external-code path needs correct instruction encoding/addressing, native call ABI, a real source allocation/boot record and on-unit worst-case fetch/audio timing. Sources: [stock VISA callback evidence](../sharc/registry.md), [external-code lead](../../resource-limits.md#ways-to-get-more-room), [assembled Atmosphere callback count](../../../tools/patch_microlooper_build.py#L89).

**[hypothesis / higher risk]** Overlay Atmosphere instructions onto inactive NAM slot storage only after a preset-dependent transition manager has been proven. Freeing NAM *owners* does not erase permanent Atmosphere instructions, and permitting a NAM slot to write over those instructions is corruption even when the Atmosphere block is currently bypassed. A valid overlay must quiesce callbacks and DMA, use a safe resident loader, retain a verified source copy, resolve all PM/data aliases, publish the new graph atomically, handle failure/reload/replacement and account for the source bytes in Entry 2 or another established boot region. The current kernel's call-timestamp reclamation heuristic is not proof that code can be overwritten. Sources for current behavior: [owner reclamation](../../../tools/sharc/nam_multi_kernel.asm#L146), [static placement overlap checks](../../../tools/patch_microlooper_build.py#L101). No such overlay loader or lifecycle proof exists in the cited implementation.

**[verified offline]** The complete current NAM1 + GR + click + Atmosphere build already occupies 524,276 of 524,288 Entry 2 bytes, with 12 bytes free after saving 4,604 bytes through zero-data encoding. An implementation that saves SRAM may still fail this independent boot-image limit; an overlay source copy and loader cannot be assumed free. Source: [build report](../../../build/microlooper-build.json), [hard limit and counting](../../../tools/sharc/microlooper.py#L21), [final linker guard](../../../tools/patch_microlooper_build.py#L125).

## Admission contract after placement is proven

**[hypothesis / required behavior]** Evaluate the candidate preset after replacing/refunding the exact old block, then apply the existing native DSP admission and the proven memory combination. Without any Atmosphere block, keep baseline NAM3 or GR/NAM2 availability. With Atmosphere present, restrict NAM only as the actual proven shared storage requires. A Atmosphere candidate must also be refused normally when existing NAM/storage use prevents it; a NAM-only extra check is not reciprocal admission. Removing or replacing the last Atmosphere restores baseline availability. Bypassed blocks remain allocated unless graph/allocator evidence proves otherwise. Several Atmosphere instances share resident instructions but each needs its own declared DM/SDRAM and measured DSP time. Do not add a Atmosphere count limit.

**[verified offline]** The existing native seam is suitable for ordinary browser refusal once a real memory rule exists: the wrapper calls `0x28dfae0c` first, preserves its status and writes the same admissible boolean. It counts the objects included by native `0x28dfa31c`, excludes the exact replaced object only when that object is eligible/in use, and scans actual model name indices. Its current extra check applies only to NAM candidates and a constant capacity; it does not implement the reciprocal contract above. Sources: [wrapper](../../../src/m4/nam_capacity.s#L1), [two guarded call sites](../../../tools/nam_capacity.py#L7), [native pricing/refund](../m4/dsp-cost.md).

**[hypothesis / staged proof]** The next work should stop at the first failing gate:

1. Produce a boot/runtime ownership map for a candidate permanent placement or explicitly specified context-swapping design. Report physical SRAM extents, private-arena sizes, all code-source bytes and complete Entry 2 size. Reject every overlap and overrun; retain the baseline kernel capacities.
2. Execute allocation, code binding/copy if used, processing and destruction under a simulator with different/odd private bases, exhausted arenas, stale data and repeated addresses. Keep native outer graph/publication limitations explicit.
3. Only then install reciprocal browser admission with exact replacement refunds. Exercise Atmosphere→NAM, NAM→Atmosphere, same-model replacement, deletion of the last Atmosphere, disabled blocks, stock neighbors and presets loaded directly rather than added through the menu. Accepted combinations must correspond to real allocated memory.
4. After offline gates, qualify graph construction/publication and all permitted instance combinations on a HX Stomp, measure worst-case timing and choose conservative native costs. Preserve ordinary no-Atmosphere NAM capacity and previously supported NAM loads. No number of simulated instruction steps proves this timing gate.

**[hypothesis / decision]** Native private allocation provides the ownership mechanism needed for a long-term design, but its current DM/PM budgets cannot absorb the fixed NAM slots or the full Atmosphere code unchanged. The current evidence supports a bounded placement/context-storage investigation, not a promise that the revised requirement is available through a small admission edit. Keep the current one-slot artifact explicitly outside the revised acceptance criteria until these gates pass.
